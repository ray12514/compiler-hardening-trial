## Scope and takeaway

This note gathers primary or first-party published measurements relevant to a standalone direct-source build comparison for FFTW, HDF5, and LAPACK, outside Spack. The available studies do not measure those libraries or the intended local workloads. Use them as context for choosing flags and designing the comparison, not as performance estimates for the meeting. The selected experiment uses GCC 12.5.0 and fixed Open MPI 4.1.8 + UCX 1.16.0; the [standalone runbooks](standalone-hardening/README.md) cover bootstrap, builds, and ReFrame execution.

Main findings:

* NIST measured GCC -fstack-protector-all versus no stack protector on FFmpeg and GNU Go. On its old Xeon Linux system, elapsed-time effects were +0.02% ± 0.92% for FFmpeg and +2.39% ± 2.49% for GNU Go. NIST did not test -fstack-protector-strong.
* A small ARM SPEC CPU2017 study describes -fstack-protector-strong overhead as negligible. It is qualitative context here, not a numerical prediction for current HPC systems.
* Red Hat reports SPEC runs with _FORTIFY_SOURCE=3 had no observed slowdown versus _FORTIFY_SOURCE=2. This does not establish no cost versus disabled FORTIFY.
* PIE evidence is architecture-sensitive and old: one 32-bit x86 SPEC CPU2006 study reported 9.4% geometric-mean overhead; its limited x86-64 check reported 2.34%.
* A SPEC CPU2017 study measured Intel CET shadow stack (SHSTK) at 2.02% geometric-mean overhead. This is not evidence for CET IBT.

No matched performance comparison for FFTW, HDF5, or LAPACK was located in searches to date, including the expanded search of distribution package records and upstream discussions below. The search is not exhaustive. No quantitative controlled runtime attribution was found for stack-clash protection, full RELRO/NOW, or CET IBT on the target library/workload set.

## Distribution builds and upstream evidence (not performance benchmarks)

These records answer whether package builds have accepted or carried hardening flags. They do not measure runtime overhead. A successful distro build, by itself, is not evidence that the flags are free or have a particular cost.

* **HDF5 1.14.6, openSUSE Tumbleweed x86-64 RPM build:** an upstream issue opened by a package maintainer reports GCC 14.2/CMake 3.31.6 and gives the complete configure invocation. `CMAKE_C_FLAGS`, `CMAKE_CXX_FLAGS`, and `CMAKE_Fortran_FLAGS` contain `-D_FORTIFY_SOURCE=3`, `-fstack-protector-strong`, and `-fstack-clash-protection`; executable and shared-library link flags contain `-Wl,-z,now`. The configuration is `RelWithDebInfo`, shared-only, thread-safe, and explicitly `HDF5_ENABLE_PARALLEL=OFF` (no MPI). The reported defect is in generated wrapper-script paths/`h5cc -show`, not a hardening failure or a performance issue. This is concrete package-build flag evidence, not a matched benchmark. [HDFGroup issue #5357](https://github.com/HDFGroup/hdf5/issues/5357)
* **HDF5 1.14.5, Fedora Rawhide 32-bit package update:** an upstream build-failure report lists GCC/gfortran 14.2.1, autotools, and Fedora CFLAGS/FFLAGS with FORTIFY=3, `-fstack-protector-strong`, and `-fstack-clash-protection` (plus LTO and other flags). The failure shown is a Fortran generic `verify` resolution error. The report does not attribute it to the hardening options and provides no performance comparison. [HDFGroup issue #4916](https://github.com/HDFGroup/hdf5/issues/4916)
* **FFTW 3.3.2 / Ubuntu Quantal (2012):** the Ubuntu changelog says Debian enabled “hardening options” for fftw3 3.3.2-2; Ubuntu's 3.3.2-3ubuntu1 changelog adds hardening flags to a long-long test so the build-log check would not complain. The entry does not enumerate the flags or report benchmark results. It establishes historical package-level hardening integration only. [Ubuntu sponsors archive, bug 1007259](https://lists.ubuntu.com/archives/ubuntu-sponsors/2012-July/024480.html)
* **CHUCK cluster, CAMK (site operator knowledge base):** the current cluster documentation warns that distribution MPI packages may include code-hardening options that “sometimes can substantially reduce performance or cause problems when linking,” and identifies `-fpic`/`-fPIE`; it offers `mpicc-nh` wrappers to omit those options. Its FFTW section shows a local FFTW build using `MPICC=mpicc-nh` with architecture optimization flags and MPI/OpenMP enabled. This is useful qualitative operational evidence that a site may selectively remove wrapper-level PIC/PIE options, but it gives no A/B timing and does not establish an FFTW kernel slowdown. The text says distro FFTW is 3.3.8 but its local install path is named 3.3.10, so the exact local version is internally inconsistent. [CAMK cluster knowledge base](https://www.camk.edu.pl/en/camknet/computational-cluster/knowledge-base/)
* **Debian policy context:** Debian's hardening documentation distinguishes defaults from opt-in controls: its general walkthrough describes common default protections and notes that PIE/BINDNOW can be enabled with `DEB_BUILD_MAINT_OPTIONS=hardening=+all`; it also documents per-feature toggles. This is distro policy, not evidence that a particular FFTW/HDF5 package used every option or that any option has a given cost. [Debian Hardening walkthrough](https://wiki.debian.org/HardeningWalkthrough); [Debian Hardening](https://wiki.debian.org/Hardening)

### HDF5 SHINES scope

The HDF Group's NSF-funded HDF5 SHINES project (Oct. 2025–Sep. 2027) targets vulnerability remediation in HDF5 core, CI/CD improvements, community capacity, and security best-practices documentation. The HDF Group's September 2026 audit is explicitly ecosystem-level and proposes a phased mitigation roadmap. These are relevant security-program developments, but the project page and reviewed audit materials do not specify a compiler/linker hardening profile or publish hardening on/off performance measurements. The word “hardening” in this initiative should not be read as evidence of a particular flag set. [HDF5 SHINES project](https://www.hdfgroup.org/projects/hdf5-shines/); [HDF Group ecosystem audit](https://www.hdfgroup.org/2026/09/02/hdf5-beyond-the-file-findings-from-our-safety-security-and-privacy-audit/)

### Terminology note

“STIG” is a compliance/profile label, not a compiler or linker option. Performance implications can only be tied to the concrete controls and build settings selected by a particular profile; this note reports individual flags where the sources expose them.

## Explicit evidence gaps

* No matched hardened-versus-unhardened performance comparison for FFTW, HDF5, or LAPACK was located in searches to date. The distro and upstream records above establish some flag use/acceptance, not overhead. This is a bounded search result rather than proof that no such study exists.
* No found study isolates -fstack-protector-strong versus -fstack-protector-all on the same modern x86-64 HPC workload. NIST measured -all; the found -strong study used a small ARM SPEC workload set.
* Red Hat's FORTIFY 2-vs-3 SPEC statement lacks public per-benchmark numbers/configuration in the article; NIST's FORTIFY 2-vs-off result is from 2014-era software and hardware.
* No quantitative controlled runtime attribution was found for stack-clash protection, full RELRO/NOW, or CET IBT on these library/workload types.
* PIE evidence includes old 32-bit x86 overhead that is architecture-specific; its x86-64 result is a limited check.
* NIST's FFmpeg transcode result does not represent HDF5 storage behavior, filesystem contention, MPI-IO, or parallel checkpointing. Other application-level studies may include I/O workloads, but none located in these searches measured FFTW, HDF5, or LAPACK directly.
